## 적용 범위와 판단 방식

2026-10-13 [배포 기록](../reports/urgent_2h_20261013/deployment/final_handoff.json)의 공개 표면은
`advanced_disabled_contract`다. 교육계획·전환 도구는 `tool_disabled`로 검증됐고 성능 표본은 없다.
따라서 공개 검색과 내부 추천·계획을 분리한다. 이 기록은 당시 상태이며 현재 원격 상태를
재확인한 결과가 아니다. 평가 시작 시 실제 도구 활성 상태와 배포 식별자를 다시 고정한다.

| 상태 | 뜻 | 판정에 사용 |
| --- | --- | --- |
| `pass` | 유효한 증거·표본으로 목표 충족 | 해당 측정 범위에 한정 |
| `warn` | KPI 목표 미달 또는 성능 회귀 첫 관측 | 개선 담당자에게 전달 |
| `fail` | 가드레일 위반 또는 유효 측정에서 행동 기준 미달 | 해당 후보·표면의 통과 보류 |
| `unknown` | 필요한 계측·증거 없음 | 통과로 계산하지 않음 |
| `inconclusive` | 표본 부족, 비교 조건 불일치, 성능 구간이 기준을 가로지름 | 조건을 갖춘 뒤 재측정 |
| `review_required` | 시설 불명확, 사람 판단 대기 | 검토 대상으로 보존; 자동 승인하지 않음 |
| `not_applicable` | 사전에 정한 적용 범위 밖 | 제외 사유·수를 함께 표시 |

서로 다른 KPI를 하나의 가중 평균 점수로 합치지 않는다. 기존 게이트와 신규 지표가 함께
적용되면 둘 다 확인한다. 신규 KPI가 통과해도 기존 gate 실패를 지우지 않는다.
미계측 가드레일은 `0건`으로 채우지 않는다. 이미 운영 중인 서비스를 이 문서만으로
자동 종료·롤백하지 않으며, 보류는 해당 변경·릴리스·주장의 판정을 보류한다는 뜻이다.

## 핵심 KPI 10개

비율은 소수 단위로 저장하고 화면에서 %로 표시한다. `@k`는 상위 k개 결과다.
품질 지표는 기본적으로 시나리오별 비율을 동일 가중 평균하고, 전체 건수와 분야별 결과를
함께 제공한다. 표본 최소선은 측정을 시작하는 조건이며 전 NCS의 성능을 보증하지 않는다.

| ID | 측정 지표 | 목표 | 경고 / 조치 기준 | 담당 |
| --- | --- | --- | --- | --- |
| K01 | 독립 자연어 검색 Hit@3 | ≥80% | 70~80% / <70% 개선 | 검색·평가 |
| K02 | 사람 근거가 확인된 추천 Hit@1 | ≥95% | 90~95% / <90% 개선 | 추천·HR 검토 |
| K03 | 상위 3개 직접근거 슬롯 비율 | ≥90% | 80~90% / <80% 개선 | 추천·평가 |
| K04 | 직접 KSA gap coverage@5 | ≥70% | 50~70% / <50% 개선 | 추천·HR 검토 |
| K05 | 사람이 판단 가능한 교육계획 비율 | ≥80% | 60~80% / <60% 개선 | 제품·HR 검토 |
| K06 | Warm MCP 응답 p95 | 공개 검색 ≤2.5초; 내부 계획 ≤5초 | 초과 경고; 충분한 표본과 구간으로 초과 확인 시 보류 | 플랫폼·성능 QA |
| K07 | 검증된 cold initialize p95 | ≤8초 | 초과 경고; 충분한 표본과 구간으로 초과 확인 시 보류 | 플랫폼 |

| K10 | 자격 API 결과 확인 완료율 | ≥90% | 10~90% 수집 계획 개선 / <10% 자격 근거 준비도 보류 | 데이터 운영 |

### K01–K05: 품질 산식과 분모

**K01 = 상위 3개에 기대 NCS 코드가 있는 질의 수 / 동결 질의 수.**
기존 holdout v3의 60질의·인사/노무/교육/총무/회계 균형 계약을 보존한다.
v3 JSON과 사람 동결 근거가 없으면 `unknown`이다. 개발셋·공식명 자기검색·반복 노출된
holdout 결과는 별도 진단이다. 전체 NCS 성능을 주장하려면 별도 세트가
`available_major_codes` 전체를 포함해야 하며, 초기 최소선은 총 120개 및 대분류별 5개다.
Hit@1·MRR·분야별 결과도 함께 보고해 상위 순위나 작은 분야의 악화를 숨기지 않는다.

**K02 = 1위 과정의 source ID와 scope가 검증 정답집합에 포함된 시나리오 수 / 사전 고정한
추천 가능 시나리오 수.** 최소 30시나리오, 5직무, 직무별 5개와 packet-backed 사람 검토가
필요하다. 오류·예상과 다른 빈 응답도 분모에 남는다. 과정명이 같은 것만으로 정답으로
인정하지 않는다. 기존 top1 gate의 95%와 수치 수준을 맞췄지만, 기존 성공 응답·과정명 기반
`top1_expected_hit_rate`와 동일한 지표는 아니다. 기존 recall 0.98·NDCG 0.99 gate도 유지한다.
raw Recall@5와 `min(5, 정답 수)/정답 수`인 달성 가능 상한을 보조로 보고한다.

**K03 = 직접근거가 있는 슬롯 수 / (3 × 사전 동결 시나리오 수).**
최소 30시나리오에 각각 3개 이상의 근거 있는 후보가 존재함을 평가 전에 확인한다.
빈 슬롯·오류·중복 과정 슬롯은 분자에 넣지 않는다. 직접근거는 유효 source ID,
같은 목표 범위의 task/KSA, 추적 가능한 `training_goal_concept_text` 관계를 모두 가진
경우다. 토큰·요소 추론·능력단위 상속만의 관계는 제외한다. 이것은 **구조적 근거 지표**이며
직접 문장 매칭 자체를 의미상 정답이라고 주장하지 않는다. 희소 분야는 별도 cohort로
유지하고, 전체 요청의 근거 가용률·보류율·오류율을 반드시 같이 보고한다.

**K04 = 각 시나리오의 직접 커버한 검증 gap 가중치 합 / 사전 동결 gap 가중치 합의 평균.**
상위 5개 과정의 동일 범위 직접 훈련목표 근거만 인정한다. gap ID를 중복 제거하고 기본
가중치는 모두 1이다. 다른 가중치를 쓰면 평가 전에 동결한다. 명시 시간·수준·시설 제약과
충돌한 과정은 분자에서 제외한다. 불명확한 시설은 잠정 coverage와 review 비율을 분리해
표시하고 실행 가능성이 확정됐다고 하지 않는다. 최소 30시나리오·5직무(각 5개), 전체
고유 gap ID 100개가 필요하다. 알려진 no-gap은 별도 정상 완료 cohort로 두고 100%로 만들지 않는다.

**K05 = rubric을 모두 충족하고 사람이 추가 사실조사 없이 채택 여부를 판단할 수 있다고
평가한 계획 수 / 사전 고정 계획 요청 수.** 최소 30계획·5직무(각 5개), 그중 제약 요청
10개를 포함한다. rubric은 guide trace 6항목, 필수 matrix/path/route,
추적 가능한 과업→KSA→과정, 명시 제약 충돌 없음, 사람 검토 상태다.
시설 `unknown/not_requested`를 검토 상태로 설명하는 것만으로 실패하지 않는다.
평가가 승인·채택 자체를 뜻하지 않으며 DB의 `accepted/reviewed/human_reviewed`로 쓰지 않는다.

Q&A 보류가 정답인 요청은 `expected_action=clarify/abstain`으로 미리 구분하고
올바른 보류율을 따로 보고한다. 추천 가능한 질의를 실행 후 보류 cohort로 옮길 수 없다.
품질 비율에는 95% 구간과 실제 n을 붙인다. 시나리오당 성공/실패는 Wilson 구간을 사용한다.
K03의 같은 시나리오 내 슬롯은 서로 독립이라고 보지 않으며, K03·K04는 시나리오별 비율의
scenario bootstrap을 사용한다. 고정 fixture의 목표 달성과 모집단 성능 보장은 구분한다.

### K06–K09: 성능 계측 규칙

- **Warm**은 MCP 요청 시작부터 전체 구조화 응답 수신까지다. 사용자 질문부터 LLM이
  최종 답변을 만드는 시간은 포함하지 않는다. `surface × workload × cache_state ×
  concurrency`별 100회 이상을 요구한다. 프로세스·캐시 재사용 증거가 없는 반복 요청은
  `observed_repeat`로 기록하고 warm으로 승격하지 않는다.
- **Cold**는 새 인스턴스와 snapshot cache miss가 확인된 최초 initialize 요청부터
  정상 응답까지다. 실제 첫 검색은 별도 진단이다. 동일 release의 독립 초기화 100회 이상에서
  p95를 판정한다. 30~99회는 잠정 기술통계, 30회 미만은 표본 부족이다. 로컬 새 프로세스
  실험이나 첫 관측 요청을 원격 cold로 대체하지 않는다. 운영 인스턴스를 강제로 재시작하는
  측정은 이 문서가 승인하지 않는다.
- **성공률 = 계약에 맞게 정상 완료한 유효 논리 요청 / 전체 유효 논리 요청.**
  **timeout 비율 = 사전 정의 deadline까지 완료하지 못한 요청 / 동일 분모.**
  rolling 7일 1,000건 이상과 Wilson 95% 구간을 사용한다. 재시도 전체를 논리 요청 1건으로
  묶고 최초 시작부터 측정한다. 정상 확인·보류는 기술 성공이지만 유용한 추천 성공은 아니다.
  입력 검증 음성 테스트·비활성 도구의 기대된 거절은 별도 집계하고, 서버 과부하·예상치 못한
  429/5xx·오류 응답은 실패에 포함한다. deadline은 평가 전에 기록하며 사후에 늘리지 않는다.
- **회귀율 = (후보 지연 / 기준 지연 − 1) × 100.** 동일 DB·fixture·파라미터·PRAGMA·환경에서
  분리 프로세스로 AB/BA를 교대하고 질의별 14쌍을 측정한다. warmup은 제외한다. 초과 시
  사전 정한 30쌍 재측정 1회로 확인한다. 두 실행을 모두 보관하고 유리한 결과까지 반복하지 않는다.
  pooled p95 개선으로 개별 질의 p50 악화를 숨기지 않는다.
- p50과 p95는 JSON 계약의 nearest-rank 규칙에 따라 정렬한 표본의
  `x[ceil(p*n)-1]`로 계산한다(`p=0.5`, `0.95`). 짝수 표본의 p50도 두 중앙값의
  평균으로 대체하지 않는다. 기존 보간식 p95와 중앙값 평균 p50은 원표본으로
  재산출하기 전까지 참고값이며 bootstrap 안에서도 같은 분위수 함수를 사용한다.
  95% 구간은 시간 블록 bootstrap, A/B는 paired bootstrap
  (고정 seed·10,000회)으로 기록한다. 구간이 기준을 가로지르면 `inconclusive`다.
  목표 초과가 구간 전체에서 확인될 때 판정을 보류한다.
- 성공 응답 지연만 계산할 경우 전체 요청 수·완료율·오류·timeout을 함께 제공한다.
  timeout을 가상의 성공 지연값으로 삽입하지 않는다. 빠른 오류 응답으로 속도가 좋아졌다는
  주장을 하지 못하도록 K08을 동반 판정한다. 부하 테스트와 빌드·대용량 검사를 동시에 실행하지 않는다.

### K10: 수집 준비도

**K10 = (`collected` 능력단위 수 + 유효 `empty` 능력단위 수) / 전체 대상 능력단위 수.**
`error`는 분자에서 제외한다. 전체 대분류와 개별 대분류 결과, 상태별 수, 기준 스냅샷을
같이 기록한다. `empty`는 해당 조건에서 자격 결과가 없음을 확인한 것이며 자격 근거를
확보했다는 뜻은 아니다. 수집 시도율·실제 자격 보유율을 별도로 보고한다.
자격 정보는 보조 근거이므로 K10 미달을 모든 교육 추천의 하드 실패로 적용하지 않는다.
목표를 채우기 위해 cooldown·batch·retry 제한을 완화할 수 없다.

## 측정 운영 순서

1. **평가 책임자:** 첫 평가 주기에 DB·코드·fixture·배포 hash와 활성 표면을 고정한다.
   기존 v3 동결 계약과 실제 사람 결정 packet을 확보한다. 결손은 그대로 기록한다.
2. **추천·HR 담당:** K02–K05의 source ID 정답, gap, 제약, expected_action을 준비한다.
   사람이 결정한 범위만 채택하고 자동 생성 후보를 신뢰 정답으로 승격하지 않는다.
3. **성능 QA:** 품질 평가와 별도 시간에 K06–K09를 측정한다. 내부/공개, warm/cold,
   function/MCP를 구분하고 오류와 timeout을 포함한 원표본을 보존한다.
4. **데이터 운영:** K10은 매주 읽기 전용 집계한다. 실제 수집은 기존 guarded 절차로만 한다.
5. **제품·평가 책임자:** 주간 회의에서 값·분모·구간·미측정 사유·가드레일을 검토한다.
   두 번의 유효 측정 주기 후 잠정 목표를 보정할 수 있으나 변경 이유·버전을 남기고
   기존 안전 원칙을 낮추지 않는다. 릴리스에는 동일 후보의 새 증거를 사용한다.

기존 재현 명령은 [HARNESS_ENGINEERING](HARNESS_ENGINEERING.md)의 Query Performance
Comparisons/Transition Evaluation과 [SEARCH_ACCURACY](SEARCH_ACCURACY.md)를 따른다.
`evaluate-training-transitions --trusted-only`의 상태 필터만으로 packet provenance가 보장되지는
않으므로 별도 감사가 필요하다. 기존 보고서 필드를 신규 지표에 바로 복사하지 않는다.

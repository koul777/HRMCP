# NCS DB 업데이트 빌더

정기적으로 갱신되는 NCS 원본의 추가·삭제·변경을 비교하고 관련 온톨로지·경량 DB·MCP까지 갱신하는 도구다. 온톨로지 편집기에 한정되지 않는다. 처음 사용하는 경우 [README의 단계별 안내](../README.md#ncs-db-업데이트-빌더-사용하기)를 먼저 읽는다.

`run_ncs_builder.bat`를 더블클릭한다. 프로젝트의 `.venv`와 기존 API 키, Vercel CLI 로그인을 사용한다.
독립 실행 EXE가 아니라 이 저장소 환경에서 실행하는 Windows 데스크톱 프로그램이다.

## 사용 흐름

1. **원본 · 변경분**: 새 NCS 정보망 Excel 전체 파일과 비교 기준 `ncs.db`를 선택한다. 처음에는 현재 로컬 원본 DB를 기준으로 한다.
2. **변경분 검토 · 온톨로지 만들기**: 전체 Excel의 내용을 비교한 뒤 추가·변경·제외된 능력단위만 정규화한다. 원본·이전 DB를 보존하고 별도 버전에 결과를 만든다.
3. **API 갱신**: 훈련과정·직업기초능력 API를 전체 NCS 대분류에 대해 수집하고 응답 완결성, 원문 KSA 보존, 검토 상태 보존을 검사한다. ① 완료 후 자동 시작하지 않으며 ② 버튼을 눌러 별도로 실행한다.
4. **③ 경량 DB 생성**: 연결 프로젝트 폴더를 확인하고 경량 DB를 만든다. 온톨로지를 포함한 DB와 ZIP·manifest를 검증한다. 자동 배포하지 않는다.
5. **④ Vercel 반영**: 별도 탭의 업데이트 버튼에서 대상 프로젝트와 운영 URL을 확인하면 임시 배포, MCP 및 빌드 식별자 검증, 운영 전환, 운영 MCP 검증 순서로 진행한다.
6. 운영 검증까지 성공한 버전만 다음 비교 기준이 된다. 기존 로컬 `data/processed/ncs.db`는 덮어쓰지 않는다.

프로젝트 루트와 `deploy/vercel_mcp_app`에는 서로 다른 Vercel 프로젝트 연결이 있을 수 있다. 마지막 성공 배포 폴더, `deploy/vercel_mcp_app` 순서로 유효한 `.vercel/project.json`과 `vercel.json`을 찾아 폴더·운영 URL을 자동 입력한다. `기존 연결 자동 찾기`로 다시 탐색하고, 없을 때만 수동으로 선택한다. 현재 배포 기능은 선택 프로젝트의 기본 `https://<projectName>.vercel.app/api/mcp` 주소를 지원한다. 사용자 정의 도메인은 자동 검증 대상에 포함하지 않는다.

## 누적 진행과 재개

`session.json`에는 단계별 시도·성공·실패·마지막 진행 상황을 저장한다. 창을 다시 열면 재개 가능한 중단 작업을 우선 선택한다. **중단한 작업 이어하기** 또는 버전 기록의 **선택 작업 이어하기**를 누른다. 선택된 중단 버전에서 API 갱신 버튼을 눌러도 새 수집 대신 재개 경로를 사용한다. 다른 작업은 버전 기록에서 선택한다. 미완료 기록은 성공으로 간주하지 않는다.

| 중단 위치 | 이어하기 동작 |
| --- | --- |
| API 수집 | `api-checkpoint/api_checkpoint.json`에 완료가 증명된 API·대분류는 건너뛴다. 중단된 대분류만 다시 조회하며 이후 미완료 범위로 진행한다. 완료한 개별 페이지 단위의 재개는 아니다. |
| API 완료 후 결과 검증 | 저장된 `api-refresh.json`과 후보 DB를 확인하고 API 재수집 없이 검증을 재개한다. 기존 버전의 완료 보고서도 조건을 만족하면 사용할 수 있다. |
| 최종 검증 | `validation-checkpoint.json`에 온톨로지 검사·참조 무결성·각 테이블 건수를 저장한다. 후보 DB 해시가 같을 때만 완료 검사를 재사용한다. 중단된 SQL 문장 하나는 처음부터 재실행한다. |
| Excel 변경 처리 완료 후 검증 | 성공한 `delta.json`이 있으면 Excel 재처리 없이 검증을 재개한다. Excel 변경 처리 도중에는 아직 내부 재개를 지원하지 않는다. |
| 경량 패키지 검증 완료 후 배포 실패 | 기존 패키지를 다시 검사하고 배포만 재시도한다. 경량 DB 생성 자체가 중단되면 해당 생성은 다시 실행한다. |

API 재개는 동일 원본·수집 설정·작업 DB 식별자·원문 및 검토 상태를 확인한다. 원본이나 작업 DB가 바뀌었으면 무조건 이어서 쓰지 않는다. 해시·보존 확인은 다시 수행하므로 재개에도 검사 시간이 든다. API 연결 관계 계산은 재개 시 다시 확인한다. 실행 중인 프로세스가 있으면 먼저 완료 여부를 확인한다. 강제 종료로 잠금 파일이 남으면 프로세스 종료를 확인한 후에만 정리한다. Tkinter 화면과 별개 스레드에서 긴 작업을 실행한다.

## 변경분의 정확한 의미

진행률은 두 가지로 구분한다. **현재 작업 진행률**은 해시 검사 바이트, SQLite 복사 페이지, API가 알려준 페이지 수, 원천 비교 행·시트 또는 변경 능력단위 처리량을 사용한다. 작업이 바뀌면 분모와 퍼센트도 새 작업 기준으로 전환된다. 미리 전체량을 알 수 없는 SQL 계산·원격 배포 대기에서는 작업명과 경과시간을 표시한다. 남은 시간이나 전체 소요시간 비율을 추정해 표시하지 않는다.

하단 **전체 진행률**은 선택된 버전의 완료 단계 수를 4로 나눈 값이다. 1/4은 25%, 2/4는 50%다. 단계별 소요시간이 같다는 뜻은 아니다. 실패한 단계는 완료로 계산하지 않는다. 단계가 생략된 경우 전체 진행률에 완료로 추가하지 않는다. 버전 기록에서 다른 버전을 선택하면 해당 버전의 완료 근거로 표시를 갱신한다.

- 파일명·행 순서·시트 위치·수집 시각 대신 능력단위별 원천 내용으로 비교한다.
- 업로드는 **전체 원본 스냅샷**이다. 일부 시트만 담은 파일을 올리면 빠진 능력단위는 제외 대상으로 계산된다. 배포 전에 변경 건수와 `delta.json`을 확인한다.
- 바뀌지 않은 원천 레코드와 식별자를 보존한다. 변경·제외된 원문은 이전 DB와 후보 DB의 보관 테이블에 남긴다. `ksa_text_raw` 값을 UPDATE하지 않는다.
- 신규·변경 원천에 필요한 온톨로지 노드를 구성한다. 현재 과업 간 유사도·교육 연결·개념 관계 요약은 전체 관계를 재계산한다. **모든 계산과 파일 쓰기가 변경된 행에만 국한되는 완전 증분 엔진은 아니다.**
- 경량 DB는 변경분을 반영한 전체 일관 스냅샷으로 재생성한다. SQLite 파일에 바이너리 패치만 적용하는 방식은 아니다.
- 사람 검토된 관계가 변경 영향 범위에 있으면 자동 처리를 중단한다. 기존 검토를 새로운 원천에 자동 전이하거나 새 승인 상태를 쓰지 않는다.
- 이전 개념 노드는 참조·검토 기록 보존을 위해 남을 수 있다. 이름이 남아 있다는 사실을 현재 직무에 연결된 근거로 해석하지 않는다.

## API 검토 범위

자동 점검은 형식·페이지 완결성·원천 보존·연결 무결성 검사다. LLM의 의미 검토나 사람의 정의 승인과 다르다.
훈련과정·직업기초능력 수집 실패 또는 완결성 미확인은 배포 가능한 버전을 만들지 않는다. API에서 누락된 항목을 삭제 근거로 쓰지 않는다.
자격·NCS006 API는 기존 retry-hygiene, checkpoint, operator-ready 조건이 필요하여 이 UI의 자동 수집에 포함하지 않는다. 기존 운영 하네스로 관리한다.

## 보관·실패 처리

산출물은 `.state/ncs-data-builder/versions/<버전>/`에 저장한다.

- `source.xlsx`: 입력 원본 사본(Excel 갱신 버전).
- `delta.json`: 변경 범위·관계 재계산·원문 보관 근거.
- `ncs.db`, `build.json`: 검증된 후보 DB, 건수·해시·상태.
- `api-refresh.json`: API 실행 근거(API 갱신 버전).
- `release.json`, `release/`: 경량 패키지·배포·원격 검증 근거.

원본·대용량 DB는 배포 폴더 밖에 남고, Vercel에는 허용된 애플리케이션 코드와 경량 ZIP·manifest만 업로드한다. 패키지 생성 후 파일이 변경되면 배포를 차단한다.
임시 배포 검증에 실패하면 운영 전환을 하지 않는다. 운영 전환 후 최종 검증이 실패한 경우에는 운영이 이미 전환되었을 수 있으므로 `promotion_performed`와 `failed_phase`를 확인하고 Vercel의 이전 배포 복귀 기능을 사용한다. 실패했다고 자동으로 롤백된 것으로 간주하면 안 된다.

동시에 하나의 Builder 작업만 허용한다. 작업 중 창을 닫으면 확인 후 창을 숨기고 안전한 중단 지점에서 작업을 정리한다. 현재 SQL·API 응답·하위 프로세스가 끝나야 중단 지점에 도달할 수 있으며, 그동안 잠금은 유지된다. ④ 배포 중에는 운영 전환과 검증을 백그라운드에서 마무리한다. 비정상 종료 시 실행 중인 Builder 프로세스가 없는지 확인한 후 `.state/ncs-data-builder/operation.lock`을 정리한다. 재생성 가능한 데이터도 자동 삭제하지 않으므로 충분한 디스크 공간과 별도 보관 정책이 필요하다.

배포 흐름: [Vercel CLI 공식 문서](https://vercel.com/docs/cli/deploying-from-cli).

## 갱신 실패 확인

`failed_no_reconcile`은 실패한 갱신 결과를 배포용으로 반영하지 않았다는 결과 코드다. 원인은 해당 버전의 `api-refresh.json`에서 확인한다. Builder는 실패 단계·로컬 오류 분류·API별 실패 대분류를 오류창에 표시한다.

2026-09-09 수정: 기존 DB에 SQLite `dbstat` 진단 가상 테이블이 있을 때 일부 Python SQLite 빌드에서 `no such module: dbstat`이 발생했다. 원천·검토 데이터가 없는 해당 진단 테이블만 검토 상태 검사와 변경 영향 탐색에서 제외한다. 원본 DB나 진단 테이블을 삭제할 필요는 없다. 실행 중이던 Builder는 종료 후 다시 실행해야 수정된 코드가 로드된다.

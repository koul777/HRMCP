# 학습 지향 개인 역량 프로필 개발 계약

상태: **설계 제안 / 미구현** · 기준일: 2026-09-13

이 문서는 기존 NCS 직무·과업·KSA·교육 추천 엔진 위에 구성원 자신의
역량 표현과 학습 지원을 연결하기 위한 개발 계약이다. 문서 작성이나
자동화 테스트 통과는 기능의 구현 완료, 운영 승인, 조직문화 확보를 뜻하지 않는다.
구성원의 개인 데이터를 실제로 도입하기 전 각 단계의 구현·검증 증거가 필요하다.

## 1. 목적과 제품 범위

구성원이 강점, 지원받고 싶은 영역, 학습 목표를 안전하게 표현하고 필요한
교육·멘토링·현업 연습을 선택하도록 돕는다. 조직에는 동의와 집계 규칙을
충족한 학습 수요만 제공하여 지원 자원을 배치할 수 있게 한다.

전체 흐름은 다음과 같다.

```text
조직의 직무·과업 요구 확인
  → 본인 전용 역량·학습 프로필 작성
  → 공유할 항목·대상·목적·기간 선택 및 미리보기
  → 동의된 근거와 목표 과업의 학습 필요 비교
  → 설명 가능한 교육·학습 대안
  → 당사자 선택과 허용된 사람 검토
  → 학습 실행·정정·재확인
  → 개인 학습 회고와 보호된 조직 집계
```

비목적은 개인의 성과평가, 징계, 보상, 승진, 채용·배치 적격성 판단과
구성원별 능력 순위 작성이다. 학습 지원 과정에서 만들어진 정보와 파생
정보를 이런 목적으로 재사용하지 않는다. 공식 자격 인정이나 법적 적격성
판단도 기존 MCP의 범위 밖이다.

“투명한 공개”는 전사 공개를 기본값으로 삼는다는 의미가 아니다. 본인이
누가 무엇을 어떤 목적으로 볼 수 있는지 이해하고 통제할 수 있어야 한다.
공유를 거절하거나 철회해도 일반적인 직무·교육 검색과 개인 학습 탐색을
이용할 수 있어야 한다.

## 2. 현재 구현과 연결해야 할 경계

현재 `training_recommendation.py`의 직무 전환 분석은 현재 NCS 직무
범위의 KSA와 목표 직무 범위의 KSA 차이를 계산한다. 이는 개인의 실제
보유 역량이나 부족 역량에 대한 측정이 아니다. 개인 프로필이 없는 경우
결과는 **직무 전환 시 확인할 학습 항목**으로 해석해야 한다.

`internal_job_roles.py`와 `scripts/onboard_internal_roles.py`는 조직의
직무 설명·과업·요구 기술을 받으며 개인 식별 필드를 거부한다. 이 경계는
유지한다. 온보딩 입력의 `skills`는 직무의 요구 기술이며 구성원의 보유
기술을 저장하는 필드로 재해석하지 않는다.

교육 추천의 `recommended_path`, `training_system_matrix`, `query_route`,
`training_system_guide_trace`와 과업·KSA·과정 근거를 재사용하되, 개인
근거의 수집·공개·수정·철회는 별도의 애플리케이션 계층에서 다룬다.
2026 NCS HRD 가이드는 계속 `framework_reference`이며 개인의 역량을
입증하는 데이터나 추천 점수의 직접 근거로 사용하지 않는다.

## 3. 주체와 위협모델

| 주체 | 허용 책임 | 기본 접근 범위 |
| --- | --- | --- |
| 구성원 본인 | 자기표현, 근거 확인, 목표 선택, 공유·철회, 정정 요청 | 자신의 프로필과 학습 계획 |
| 본인이 지정한 코치·멘토 | 동의된 목표와 지원 계획 검토 | 지정 항목·목적·기간에 한정 |
| 교육 담당자 | 과정·시간·시설 등 학습 지원 | 동의된 운영 정보 또는 보호된 집계 |
| 조직 직무 담당자 | 직무·과업 요구와 NCS 매핑 확인 | 직무 데이터; 개인 프로필 접근은 별도 권한 |
| 플랫폼 운영자 | 서비스 운영·보안·복구 | 원문 접근 없는 운영 메타데이터를 기본값으로 사용 |
| AI Agent·MCP | 허용된 맥락의 검색·추천 초안 생성 | 요청별 최소 입력; 승인·권한 부여 권한 없음 |

관리자 직위, 교육 담당자 역할, 서비스 운영 권한 자체는 개인 프로필을
읽을 권한이 아니다. 조직 식별자나 사용자 ID를 요청 본문에서 바꾸어
다른 사람의 자료를 조회할 수 없어야 한다. 인증된 주체와 조직 경계는
서버가 결정한다.

주요 위협은 관리자에 의한 공유 강요, 교육 목적을 가장한 인사평가,
다른 조직·다른 구성원 정보 조회, 토큰 탈취, AI 프롬프트를 통한 권한
우회, 로그·보고서·내보내기의 원문 누출, 소수 집단 재식별, 반복 집계의
차분 공격, 철회 전 자료의 캐시·파생본 잔존이다. 코드로 막을 수 있는
접근·처리 위협과 실제 권력관계·비보복 운영 문제를 구분하여 검증한다.

## 4. 데이터 경계와 최소 계약

개인 프로필은 **본인 전용(private-by-default)**이다. 개인 데이터 저장소는
공용 NCS 지식 DB·Builder 후보 DB·compact DB·ZIP·manifest와 분리한다.
공용 Vercel snapshot, Git 저장소, 공개 데모·리포트, 공개 MCP 응답에 개인
프로필·동의 내역·개인 학습 이력·식별 가능한 파생 정보를 포함하지 않는다.
Builder의 단일 생산 배포 책임을 개인 프로필 수집·배포 권한으로 확대하지 않는다.

개인 프로필 저장소와 이를 처리하는 서비스의 인증·조직 경계·권한 집행이
준비되기 전에는 합성 데이터만 사용한다. 공용 MCP에는 개인 식별자나
자유문장 원문을 전달하지 않고, 가능한 경우 승인된 NCS 과업·개념 ID와
학습 제약만 전달한다. 외부 AI 제공자에 필요한 정보를 보내는 경우에는
전달 항목·처리 목적·보존 경계가 확인된 경로만 사용한다.

아래 명칭과 필드는 신규 설계이며 현재 구현 완료를 나타내지 않는다.

| 계약 | 최소 필드와 불변조건 |
| --- | --- |
| `learning_skill_assertion_v1` | 조직·가명 주체 ID, 주장 ID·버전, 과업/개념 참조, 표현 상태, 자기보고/관찰 등 출처, 확신도, 작성·관찰 시점, 근거 참조; 기본 공개 범위는 본인 |
| `learning_consent_grant_v1` | 부여자, 허용 대상, 필드/자료 버전 범위, 허용 목적, 시작·만료·철회 시점, 정책 버전; 포괄 동의 금지 |
| `learning_gap_analysis_v1` | 목표 직무·요구 근거 버전, 사용한 개인 주장 버전, 동의 참조, 비교 종류, 미확인 항목, 설명·제약; 직무 간 차이와 개인 학습 필요를 구분 |
| `learning_plan_v1` | 본인 선택 목표, 과업·KSA·과정 근거, 대안, 시간·방법 제약, 검토 필요, 채택/보류 상태, 입력·모델·정책 버전 |
| `learning_correction_request_v1` | 대상 주장/분석 버전, 정정 유형, 요청 상태, 처리 이유·시점, 관련 파생본 참조; 요청만으로 원래 기록을 사실로 확정하지 않음 |
| `learning_access_event_v1` | 주체의 가명 참조, 자원 ID, 행위, 목적, 허용/거부, 정책·동의 버전, 시각·상관 ID; 원문 프로필이나 자유문장 미저장 |
| `learning_aggregate_v1` | 기간·허용 목적, 집계 정의, 구성원 수, 억제 여부·사유, 정책 버전; 개인 행과 원문 근거 없음 |

식별자 가명화는 익명화와 다르다. 가명 주체 ID, 접근 기록, 근거 파일도
개인 관련 자료로 다루며 재결합 키의 접근 권한을 분리한다.

## 5. 강점·지원 필요·미응답 상태모델

역량 표현은 하나의 점수로 압축하지 않는다.

- `strength_self_reported`: 본인이 강점이라고 표현함.
- `support_requested`: 특정 과업에서 지원받고 싶다고 표현함.
- `learning_goal`: 배우고 싶은 방향이며 현재 부족하다는 판단을 내포하지 않음.
- `uncertain`: 본인이 수준이나 근거를 아직 판단하기 어려움.
- `not_answered`: 입력되지 않음. 수준 0 또는 부족 역량으로 변환하지 않음.
- `not_applicable`: 현재 목표·과업에 해당하지 않음.

표현 상태와 증거 상태를 분리한다. 자기보고, 관찰 근거 존재, 상충 근거,
오래된 근거, 확인 대기는 각각의 provenance로 보존한다. AI가 추정한
매핑은 `candidate` 또는 `review_required`로 표시하고 본인 표현을 덮어쓰지
않는다. 현재 직무를 맡았다는 이유만으로 그 직무의 모든 KSA를 보유했다고
간주하지 않는다. 수료 기록만으로 숙련도나 현업 수행능력을 확정하지 않는다.

개인 역량 자료를 `ontology_concepts.definition`이나 원천 KSA로 승격하지
않는다. `ksa_items.ksa_text_raw`는 어떤 경우에도 변경하지 않는다.

## 6. 동의·미리보기·철회

동의 화면은 공유할 자료, 실제 수신자, 목적, 기간, 가능한 내보내기 여부,
철회 후 처리 범위를 한 화면에서 확인할 수 있게 한다. 기본 선택은 공유
안 함이다. 필드별 공유와 특정 계획만 공유를 지원하고, 새 자료가 추가됐다는
이유만으로 기존 동의 범위를 자동 확대하지 않는다.

공유 전 미리보기는 실제 수신자에게 적용되는 동일한 서버 투영·권한 로직을
사용한다. 설명용 가짜 화면만 제공해서는 안 된다. 관리자에게 보이지 않는
강점·지원 요청·근거가 미리보기에서도 일관되게 숨겨져야 한다.

철회와 만료는 다음 요청부터 조회·추천 입력·내보내기에서 집행한다. 장시간
작업은 시작 시와 결과 제공 시 권한을 다시 확인한다. 파생 계획·캐시·검색
인덱스는 동의와 원본 버전의 lineage를 통해 무효화·정리하고, 지원 가능한
정리 지연시간을 운영 계약에 명시한다. 이미 허용된 다운로드나 사람이 본
정보를 기술적으로 되돌릴 수 있다고 약속하지 않는다. 초기 단계에는 개인
원문 대량 내보내기를 제공하지 않으며 제한 사항을 공유 전에 설명한다.

## 7. 학습 필요 분석·추천·사람 검토

비교 결과는 `role_scope_difference`와 `personal_learning_hypothesis`를
구분한다. 후자는 유효한 개인 근거와 처리 권한이 있을 때만 생성한다.
부족한 증거는 `unknown`으로 남기고, 목표 과업·근거·자기표현의 차이를
설명한다. 강점의 전이 가능성과 필요한 지원을 함께 제시한다.

추천은 기존 과업·KSA·교육목표·과정·수준·시간·방법·시설 근거를 보존한다.
근거가 약한 과정은 보완/인접 참고로 표시하고 개인에게 필수라고 자동
확정하지 않는다. 추천 설명에서 학습 계획의 초안 상태와 입력 한계를 볼
수 있어야 한다.

사람 검토는 구성원이 허용한 범위에서 목표·지원 계획을 확인하는 절차다.
공유 권한과 검토 권한은 서로 다르며, 검토자는 보이지 않는 프로필 항목을
승인하거나 요청 권한을 자동 취득할 수 없다. 자동화는 `human_reviewed`,
`accepted`, `reviewed`를 명시적 사람 결정 없이 부여하지 않는다. 실제
사람 결정도 대상 버전·결정자·시각·근거에 연결하고 조직의 인사 승인으로
확대 해석하지 않는다.

## 8. 이의제기·정정

구성원은 자기표현을 수정하고 AI가 붙인 개념·과업 매핑, 갭 해석, 추천
이유에 이의를 제기할 수 있다. 정정 중인 항목은 논쟁 중 상태를 표시하고
이를 개인 부족이나 비협조 신호로 집계하지 않는다.

정정은 새 버전을 만들고 이전 버전을 현재 사실처럼 계속 사용하지 않는다.
관련 추천·공유 자료·집계를 재계산하거나 무효화하며 처리 내역을 본인이
확인할 수 있게 한다. 분쟁 기록의 원문은 일반 감사로그에 복제하지 않는다.
자동 처리할 수 없는 이의제기는 책임자와 처리기한이 있는 지원 경로로
넘기고, 본인의 요청이 자동 승인으로 바뀌지 않게 한다.

## 9. 목적 제한과 조직 집계

성과평가·징계·보상·승진 목적의 조회, 분석, 내보내기를 거부한다. 요청자가
`purpose=learning`이라고 적는 것만으로 허용하지 않는다. 서버에서 신뢰하는
호출 경로·권한·허용 행위와 목적을 함께 검증한다. AI의 지시나 관리자 역할로
이 정책을 우회할 수 없어야 한다. 학습 필요 점수의 인사 시스템 전달 경로를
만들지 않는다.

조직 집계는 개인 순위 대신 학습 수요와 지원 접근성, 참여·현업 적용의
변화를 다룬다. 초기 집계 정책은 서로 다른 구성원 **10명 이상**을 기본
공개 조건으로 제안하며, 이 숫자는 익명성을 보증하는 기준이 아니다.
집계 정의와 대상 집단의 재식별 위험을 확인하여 조정한다.

소집단 억제 외에 자유문장 제거, 세부 교차필터 제한, 반복 조회·기간 간
차분 제한, 보완 억제, 조회 이력 기반 방어가 필요하다. 집계 권한이 있다고
개인 원문으로 drill-down할 수 없어야 한다. 표본이 작거나 비교 가능한
기준이 없으면 효과를 `insufficient_evidence`로 표시한다. 공유율·약점 입력
건수를 관리자 성과 목표로 삼거나 참여하지 않은 사람을 추적하지 않는다.

## 10. 감사로그·보존·삭제

감사로그는 허용/거부와 책임 추적에 필요한 메타데이터만 저장한다. 스킬
자유문장, 근거 문서 본문, 추천 요청 전체, 인증 토큰, 연락처를 저장하지
않는다. 오류·관측·AI 추적 로그와 공개 보고서에도 동일한 최소화 규칙을
적용한다. 본인이 이해할 수 있는 접근 이력과 운영자용 보안 기록의 노출
범위를 구분한다.

구현 전 개인 프로필, 근거 파일, 파생 계획, 동의 기록, 접근 로그, 백업별
보존기간과 삭제 SLA를 명시해야 한다. 기간이 미정인 채 실제 개인 데이터를
저장하지 않는다. 동의 철회와 삭제 요청은 별도 동작으로 설명하되 둘 다
향후 이용 통제에 반영한다.

삭제는 원본뿐 아니라 첨부·파생 자료·캐시·인덱스·복제본을 추적한다.
백업에서 복구할 때 삭제·철회 정보를 재적용하여 자료가 다시 활성화되지
않아야 한다. 즉시 삭제하지 못하는 보안 감사 기록은 보존 이유·기한·접근
범위를 제한하고 원문을 제거한다. 계정 종료·조직 이동 시에도 접근과 보존
상태를 명시적으로 처리한다.

## 11. 단계별 구현과 완료 증거

| 단계 | 구현 범위 | 다음 단계 진입 증거 |
| --- | --- | --- |
| 0. 계약·운영 책임 | 본 문서, 용어·목적, 조직 책임자, 이의제기와 비보복 운영, 데이터 흐름 | 기능과 조직 운영의 책임 구분, 미정 사항 목록, 실제 데이터 도입 조건 |
| 1. 개인 전용 프로필 | 분리 저장소, 인증·조직/본인 경계, 상태모델, 근거 버전 | 합성 데이터로 권한·미응답·분리 저장·삭제 테스트 통과 |
| 2. 선택 공유 | 필드·대상·목적·기간 동의, 실제 미리보기, 철회·만료 | 다른 주체/조직 조회 거부, 캐시·진행 작업·파생본 철회 검증 |

| 4. 사람 검토·학습 실행 | 허용된 코치 검토, 계획 이력, 실행·회고 | 실제 결정 provenance, 권한 밖 검토 거부, 수료와 숙련도 분리 |
| 5. 제한된 시범 운영·집계 | 지원 효과, 소집단 보호, 운영 대응 | 자동 검증과 구성원 피드백을 각각 확인; 미확인 문화 상태 명시 |

기존 검색 성능 개선·Builder 배포와 본 기능의 구현 완료 상태를 분리하여
릴리스 노트에 기록한다. 개인 기능이 없는 배포를 개인 스킬 공개 시스템
완료로 홍보하지 않는다.

## 12. 자동화 가능한 acceptance criteria

아래 테스트는 구현 시 필수 수용 기준이다. 현재 통과했다는 주장이 아니다.

| ID | 시나리오와 기대 결과 |
| --- | --- |
| AC-01 | 신규 프로필을 본인 외 주체·타 조직·관리자 역할로 조회하면 거부한다. 요청 본문의 주체/조직 ID 변조도 동일하다. |
| AC-02 | 미응답·불확실·해당 없음이 수준 0, 부족 역량, 비협조 점수로 변환되지 않는다. |
| AC-03 | 직무 온보딩의 요구 기술과 개인 보유 주장을 혼합하지 않으며 개인 프로필 없는 분석은 직무 차이로 표시한다. |
| AC-04 | 미리보기와 실제 수신자 응답의 허용 필드가 일치한다. 중첩 근거·첨부·오류 응답에서도 숨긴 정보가 노출되지 않는다. |
| AC-05 | 동의 만료/철회 후 새 조회·내보내기·추천 입력이 거부되며, 진행 작업은 결과 제공 전 재검증한다. |
| AC-06 | 원본 정정/삭제/철회가 연결된 파생 계획·캐시·인덱스에 지정 SLA 안에 반영되고 오래된 자료가 현재 사실로 복원되지 않는다. |
| AC-07 | 성과평가·징계·보상·승진 행위는 관리자·AI 지시·목적 문자열 위장에도 거부된다. |
| AC-08 | 추천마다 직무 근거와 개인 근거의 ID·버전·출처가 분리되어 있으며 필요한 권한과 provenance가 없으면 개인화하지 않는다. |
| AC-09 | 자동 생성 경로는 `human_reviewed`, `accepted`, `reviewed`를 쓰지 않는다. 사람 결정 누락·대상 버전 불일치·권한 없음은 검토 반영을 거부한다. |
| AC-10 | 공용 Builder/Vercel 패키지·Git·공개 응답·보고서·로그를 합성 식별자와 표식으로 검사하여 개인 데이터 유출이 없음을 확인한다. |
| AC-11 | 소집단·교차필터·반복 조회·차분 공격 시나리오에서 집계가 억제되며 집계로부터 개인 행을 조회할 수 없다. |
| AC-12 | 감사로그·오류·AI 추적에 원문·토큰이 없고, 필요한 접근/거부 메타데이터는 남는다. |
| AC-13 | 백업 복구 후 삭제와 철회가 재적용되고 계정 종료·조직 이동 뒤 기존 권한이 살아나지 않는다. |
| AC-14 | 공유 거부·철회 상태에서도 일반 NCS 검색과 본인 전용 학습 탐색은 계속 이용 가능하다. |
| AC-15 | 수료·자기보고·관찰·AI 추정은 서로 다른 근거 상태로 유지되며 수료만으로 숙련도나 개인 평가를 확정하지 않는다. |

## 13. 실제 조직에서만 검증할 수 있는 기준

다음 사항은 코드나 테스트의 통과 여부로 확정하지 않는다.

- 구성원이 공유 거부·약점 표현·정정 요청 후 실제 불이익을 받지 않는가.
- 관리자가 공유를 사실상 의무화하거나 개인별 공개율을 추적하지 않는가.
- 구성원이 누구에게 무엇이 보이는지 이해하고 선택권을 실제로 행사하는가.
- 지원 요청이 교육 시간·멘토링·현업 기회 등 실제 자원으로 이어지는가.
- 이의제기와 오용 신고에 응답하는 책임자가 있으며 처리 결과를 당사자가 확인하는가.
- 구성원이 느끼는 안전성과 신뢰가 유지되는가. 설문 참여도 자발적이며 작은 집단을 노출하지 않는가.
- 학습 후 현업 적용과 지원 효과가 관찰되는가. 변화의 원인을 프로그램만의 효과로 과장하지 않는가.

시범 운영 보고서는 `technical_controls_verified`와
`organizational_practice_evidence`를 분리한다. 증거가 없으면 각각 미확인으로
남기며 단일 “학습문화 확보 완료” 상태로 합치지 않는다.

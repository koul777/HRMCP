# 1단계 — 자연어 검색 정렬 버그 수정

- 작업일: 2026-09-11
- 상태: 완료 — 2단계 승인 대기
- 범위: `ncs_search`의 fallback 정렬과 명시된 회귀 사례만 다룬다.

## 원인 분석

제보된 원인은 현재 코드에서 재현됐다. `token_or` fallback은 구문 전체를 기준으로 한 기존 `CASE`가 모든 후보에서 같은 값이 되며, 이후 `LENGTH(unit_name_raw)` 순으로 정렬된다. `api_definition`에 널리 등장하는 `설계`, `계획`, `수립`만 일치한 짧은 이름의 능력단위가 상위에 노출되는 직접 원인이다.

추가로 확인한 제약이 있다. 실제 DB의 `인사평가(0202020105_23v3)` 행에는 `성과평가`, `제도`, `설계`가 연속 토큰으로 존재하지 않고 `ncs_query_aliases`에도 `성과평가` 별칭이 없다. 따라서 요청된 가중치 정렬만 적용하면 이 행은 후보군에 들어오지 않아 `성과평가 제도 설계` 회귀 조건을 충족할 수 없다.

## 변경 계획

1. `expanded_token_and`와 `token_or`에서만 토큰별 필드 가중 점수를 계산한다. 사용자 토큰과 LIKE 패턴은 계속 SQL 파라미터로 바인딩한다.
2. 능력단위 필드 가중치는 이름/별칭 3, 소분류/세분류 2, 대분류/중분류 1, API 정의 1로 둔다.
3. `관리`, `제도`, `설계`, `계획`, `수립`, `운영`, `업무`, `직원`, `담당`은 0.3배로 낮추고, fallback에서 비범용 토큰이 하나도 일치하지 않은 행은 제외한다. 이 목록은 코퍼스 빈도와 사용자 질의에서의 행위·맥락 표현이라는 근거를 주석으로 남긴다.
4. element/criteria/ksa fallback에도 동일한 점수·필터 구조를 적용한다.
5. 실무 표현과 공식 명칭의 차이를 해소하기 위해 `성과평가 -> 인사평가`를 코드 검토된 최소 단방향 질의 확장으로 추가한다. 이는 후보 검색용이며 DB나 온톨로지 상태를 변경하지 않는다. 확장어도 바인딩 파라미터로 처리한다.
6. phrase와 기존 token AND tier의 조건 및 정렬 우선순위는 변경하지 않는다.
7. 로컬 서버를 변경한 뒤 Vercel 미러를 동일하게 반영하고 바이트 동일성 테스트를 확인한다.

## 구현 결과

변경 파일:

- `src/ncs_mcp/server.py`
- `deploy/vercel_mcp_app/src/ncs_mcp/server.py`
- `tests/test_ncs_search_recall.py`
- `reports/debug_2026-09/01_search_ranking_fix.md`

핵심 변경:

- fallback 점수식을 토큰 수에 맞춰 동적으로 생성하되, 질의 패턴과 점수 가중치는 모두 SQL 파라미터로 바인딩했다.
- unit 검색은 `unit_name_raw=3`, `alias_search_text=3`, `sub_name/small_name=2`, `middle_name/major_name=1`, `api_definition=1`을 적용했다.
- element/criteria/ksa에도 각 주 텍스트 필드를 중심으로 동일한 fallback 점수·필터 구조를 적용했다.
- 범용어는 0.3배로 낮추고, OR/expanded fallback에서 비범용 토큰이 하나도 일치하지 않는 후보는 제외했다.
- `성과평가`를 공식 NCS 명칭 `인사평가`로 후보 확장하는 단방향 recall 규칙을 추가했다. 원천 DB와 온톨로지는 변경하지 않았다.
- phrase와 기존 token AND tier의 조건 및 정렬은 유지했다.
- OR 후보 조건을 비범용 토큰 집합과 동치인 형태로 줄여 중복 LIKE 평가를 제거했다.

## 미해결 이슈와 위험

- `성과평가 -> 인사평가`는 이번 명시 사례를 위한 보수적 단방향 확장이다. 더 넓은 동의어 확대는 2단계 평가 세트의 Hit@1/Hit@3/MRR 근거를 얻은 뒤 결정해야 한다.
- 범용어만으로 구성된 질의는 phrase 또는 token AND가 성공하면 기존처럼 반환되지만, 그 둘이 실패한 OR/expanded fallback에서는 결과가 비게 된다. 이는 무관한 대량 결과를 막기 위한 의도된 동작이다.
- 이번 단계에서는 원격 Vercel 배포를 실행하지 않았다. 배포 미러 소스만 로컬과 동일하게 갱신했다.
- 2단계 이상의 작업은 지시대로 시작하지 않았다.

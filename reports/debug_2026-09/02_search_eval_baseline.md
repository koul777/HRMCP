# 2단계 — 자연어 검색 품질 평가 세트 구축

- 작업일: 2026-09-11
- 상태: 완료(초기 Hit@3 게이트는 경고 모드, 목표 미달)
- 범위: 자연어 능력단위 검색 평가 데이터, Hit@1/Hit@3/MRR 감사 도구, CI 경고 게이트

## 원인 분석

1단계는 명시된 5개 질의의 정렬 결함을 수정했지만, 실무 표현 전체에 대한 개선 여부를 수치화하지 못한다. 특히 `성과평가 -> 인사평가`처럼 후보 확장이 필요한 사례와 `연봉 협상`, `신입사원 온보딩`처럼 공식 NCS 명칭과 사용자 표현이 다른 사례는 개별 회귀 테스트만으로 일반화 성능과 부작용을 판단할 수 없다.

기존 `scripts/audit_ncs_search_precision.py`는 의도적으로 무라벨 구조 위험 프록시만 계산하며, Precision/Recall/MRR을 측정하지 않는다는 안전 계약을 가진다. 기존 모드의 의미를 바꾸면 기존 보고서와 테스트 계약을 훼손하므로 별도 자연어 회귀 평가 모드가 필요하다.

또한 CI가 만드는 소형 smoke DB에는 전체 평가 코드가 없다. 따라서 로컬의 실제 DB에서는 전 항목을 검증·측정하고, CI에서는 전체 DB가 이용 가능할 때 같은 게이트를 실행하되 초기에는 환경변수로 실패 대신 경고를 내도록 구성해야 한다.

## 변경 계획

1. `tests/fixtures/ncs_search_eval_nl.json`에 인사·노무·교육·총무·회계 각 8건, 총 40건의 실무 표현을 작성한다.
2. 모든 `expected_unit_codes`는 현재 `data/processed/ncs.db`의 실제 능력단위 코드 존재 여부와 명칭·분류를 읽기 전용으로 검증한다. 이 기대값은 코드 회귀 기준이며 사람 검토·승인 상태를 의미하지 않는다.
3. 기존 precision-risk proxy 모드는 그대로 유지하고, 자연어 평가 입력에 대해서만 Hit@1, Hit@3, MRR과 카테고리별 표를 생성하는 별도 모드를 추가한다.
4. 1단계 직전 동작은 현재 서버에서 1단계의 점수·범용어 필터·정적 동의어만 비활성화하는 감사 전용 comparator로 재현한다. 제품 서버나 DB를 되돌리거나 수정하지 않는다.
5. CI에 Hit@3 0.7 게이트를 추가한다. `NCS_SEARCH_EVAL_ENFORCE=false`에서는 경고만 내고, `true`일 때 임계치 미달 또는 평가 DB 부재를 실패로 처리한다.
6. 평가기 자체 테스트, 전체 unittest, lint, smoke, 온톨로지 validate, quality-gates를 순서대로 확인한다.

## 수정 전/후 품질 기준선

평가 조건은 `scope=unit`, `limit=10`, 동일한 40개 질의다. MRR은 MRR@10이다.

| 버전 | Hit@1 | Hit@3 | MRR@10 | 검색 오류 |
| --- | ---: | ---: | ---: | ---: |
| 1단계 수정 전 재현 | 0.3500 (14/40) | 0.4250 (17/40) | 0.3965 | 0 |
| 현재 | 0.4750 (19/40) | 0.5000 (20/40) | 0.5062 | 0 |
| 변화 | +0.1250 | +0.0750 | +0.1097 | 0 |

| 카테고리 | 수정 전 Hit@1 | 수정 전 Hit@3 | 수정 전 MRR | 현재 Hit@1 | 현재 Hit@3 | 현재 MRR |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 인사 | 0.2500 | 0.3750 | 0.3264 | 0.3750 | 0.3750 | 0.3875 |
| 노무 | 0.3750 | 0.5000 | 0.4375 | 0.5000 | 0.6250 | 0.5938 |
| 교육 | 0.5000 | 0.5000 | 0.5000 | 0.8750 | 0.8750 | 0.8750 |
| 총무 | 0.1250 | 0.2500 | 0.2188 | 0.1250 | 0.1250 | 0.1500 |
| 회계 | 0.5000 | 0.5000 | 0.5000 | 0.5000 | 0.5000 | 0.5250 |

1단계 변경은 전체 지표와 특히 교육·노무 검색을 개선했다. 그러나 현재 Hit@3는 0.5000으로 초기 목표 0.7에 미달한다. 총무는 오히려 0.2500에서 0.1250으로 하락했으므로 이 평가 세트를 다음 검색 개선의 회귀 방어선으로 사용해야 한다.

## 미해결 이슈와 위험

1. **Hit@3 목표 미달**: 현재 0.5000으로 0.7보다 0.2 낮다. 경고 모드를 강제 실패로 전환하면 현재 CI는 실패한다.
2. **카테고리 편차**: 교육 Hit@3는 0.8750이지만 총무 0.1250, 인사 0.3750, 회계 0.5000이다. 다음 검색 품질 작업은 총무·인사의 실무어-공식명 동의어와 회계 세금 약칭을 우선해야 한다.
3. **현재 미적중 예시**: `연봉 협상`, `신입사원 온보딩`, `승진 심사`, `사무용품 구매`, `법인 차량 운영`, `원천세 신고`, `부가세 신고` 등이 Top 3에 기대 단위를 내지 못한다. 상세 20건은 결과 보고서에 남겼다.
4. **평가 라벨 한계**: 기대 코드는 DB의 실재 여부와 분류를 확인했지만 사람 평가자가 승인한 gold label은 아니다. 따라서 이 수치는 코드 회귀 품질만 나타내며 생산 적합성을 주장하지 않는다.
5. **CI DB 가용성**: GitHub Actions에 전체 SQLite가 materialize되지 않으면 게이트는 `evaluation_database_unavailable` 경고만 기록한다. 향후 강제 게이트 전환 전 전체 평가 DB를 안전하게 공급하는 CI 경로가 필요하다.
6. **성능·배포 영향**: 제품 검색 런타임 코드는 2단계에서 바뀌지 않아 사용자 요청 지연 변화는 없다. 로컬에서 현재/수정 전 총 80회 검색과 보고서 생성을 합친 감사 실행은 약 12초였다. 배포 영향은 CI 단계 추가뿐이며 Vercel 런타임 파일과 MCP 계약은 불변이다.
7. **기존 품질 경고**: 품질 게이트의 경고 5건은 사람 검토 3종, 자격 수집 커버리지, packet-backed 전환 시나리오 부족으로 이번 검색 평가 변경과 무관하다.

2단계는 여기서 종료한다. 3단계는 별도 승인 전 진행하지 않는다.

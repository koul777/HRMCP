# 8단계 — 토큰 문서빈도 가중으로 일반화 개선

작성일: 2026-09-11

## 배경

7단계에서 독립 holdout 51개 기준 Hit@3가 0.451로, 학습 40개 기준 0.875와 0.424 차이가 났다.
실패 28건의 다수가 범용 행정 토큰이 무관한 대분류를 끌어오는 유형이었다.

## 원인 분석

### 처음 가설은 틀렸다

"범용 토큰이 코퍼스에 너무 흔해서"라고 보고 상한 1.0짜리 IDF 계수를 검토했으나, 실제 문서빈도를
측정하니 가설이 성립하지 않았다.

| 토큰 | df | df% |
|---|---:|---:|
| 처리 | 195 | 1.45% |
| 기준 | 30 | 0.22% |
| 기록 | 12 | 0.09% |

`처리`는 13,435개 중 195개로 흔한 축이 아니다. 상한을 둔 계수로는 0.919가 되어 감점이 거의 없다.

### 실제 메커니즘

기존 점수 계산은 매칭된 토큰마다 `field_weight × generic_factor`를 더하는데, `generic_factor`는
손으로 고른 9개 토큰(`관리`, `제도`, `설계`, `계획`, `수립`, `운영`, `업무`, `직원`, `담당`)에만
0.3이고 나머지는 전부 1.0이었다. 따라서 `퇴직`(df=2)과 `처리`(df=195)가 같은 가중치를 받는다.

```
퇴직업무지원   ← 퇴직 1개 매칭 = 1.0
심냉처리       ← 처리 1개 매칭 = 1.0   동점
```

동점이 되면 `LENGTH(unit_name_raw)` tiebreak가 짧은 이름을 올린다. `퇴직 정산 서류 처리`가
심냉처리·퀜칭열처리·진공열처리를 반환한 경로가 이것이다.

문제는 토큰이 흔한 것이 아니라 **토큰의 변별력이 점수에 반영되지 않는 것**이었다.

## 변경 계획

1. 손으로 관리하는 목록 대신 코퍼스에서 문서빈도를 측정해 토큰 가중치를 정한다.
2. 가중치는 `log(N / df) / log(N)`으로 (0, 1] 범위에 정규화해 기존 점수 규모를 유지한다.
3. 문서빈도는 가장 높은 가중치(3.0)를 가진 `unit_name_raw`에서 측정한다.
4. 기존 generic 목록은 **점수에서는 대체**하되, "단독 fallback 히트 가능 여부"를 정하는
   `meaningful_clause` 용도로는 그대로 둔다. WHERE 쪽 의미 변경은 별건이다.
5. 능력단위 검색에만 적용한다. 측정된 실패가 전부 unit scope다.
6. 40개 회귀 세트와 51개 holdout을 모두 측정해 한쪽만 오르지 않는지 확인한다.

## 구현 결과

`src/ncs_mcp/search/core.py`와 Vercel 미러에 `_ncs_search_token_idf_weights()`를 추가하고,
`_ncs_search_fallback_ranking()`이 토큰별 가중치를 받도록 했다.

```python
frequency = max(int(row[0] or 0), 1)
weights[token] = max(
    _NCS_SEARCH_IDF_FLOOR,
    math.log(total / frequency) / ceiling,
)
```

토큰당 `COUNT(*)` 한 번이 추가된다. 모듈 로드 시점에 코퍼스를 미리 훑지 않으므로 Vercel
cold start 비용이 늘지 않는다.

### IDF가 사람이 고른 값을 재현한다

의도하지 않았지만, 측정된 가중치가 기존 손튜닝 값과 상당히 일치한다.

| 토큰 | df | IDF 가중 | 기존 수동값 |
|---|---:|---:|---:|
| 관리 | 2,813 | 0.164 | 0.3 |
| 설계 | 1,078 | 0.266 | 0.3 |
| 계획 | 649 | 0.319 | 0.3 |
| 수립 | 593 | 0.328 | 0.3 |
| 운영 | 444 | 0.359 | 0.3 |
| 업무 | 72 | 0.550 | 0.3 |
| 제도 | 15 | 0.715 | 0.3 |
| 직원 | 3 | 0.884 | 0.3 |

실제로 흔한 5개는 수동값과 거의 같고, 실제로는 드문 `업무`·`제도`·`직원`은 과도한 감점이
교정된다. 반대로 목록에 없던 `처리`·`분석`·`평가`가 이제 감점된다.

## 남은 실패와 다음 과제

holdout 23건이 남아 있고, 이제 IDF로 풀 수 없는 다른 층위가 드러났다.

### 1. 부분 문자열 매칭이 단어 경계를 무시한다

`LIKE '%토큰%'`이 형태소 경계를 보지 않는다.

| 질의 | 반환 | 원인 |
|---|---|---|
| **출입** 통제와 보안 점검 | 수출입계약, 수출입사전준비 | `출입` ⊂ `수출입` |
| 퇴직 정산 **서류** 처리 | 서류전분 제조, 곡류·서류·견과류가공 | 문서 `서류` vs 薯類 |

첫 번째는 명백한 결함이고 두 번째는 동형이의어다. 단어 경계를 고려한 매칭이나 형태소 분석이
필요하며, IDF와 독립된 작업이다.

### 2. HR 문맥이 랭킹에 전달되지 않는다

`업무용 차량 배차 관리`가 철도차량으로, `워크숍 행사 준비`가 웨딩·연회로 간다. 분류 필터
파라미터나 질의 라우터의 분류 추론을 검색에 넘기는 경로가 필요하다.

### 3. 상위어·하위어 혼동

`엑셀 스프레드시트 문서 작성`이 `사무자동화 프로그램 활용` 대신 `문서 작성`을 반환한다.

### 게이트 전환

`NCS_SEARCH_EVAL_ENFORCE=true` 전환은 holdout 기준 0.549가 0.7 게이트에 미달하므로 아직
이르다. 위 세 과제를 처리한 뒤 재검토한다.
